# Performance measurements — P9.3c (2026-11-23)

PRD §14 targets:
- TTFB < 400 ms p95 on member pages
- Livewire calls < 300 ms
- search < 800 ms p95 at 100k profiles
- LCP < 2.5 s on 4G

All numbers below are measured, not estimated. Machine: the local XAMPP dev box (MariaDB 10.4.32), with less than 1 GB of RAM free during the runs.

## Search at 100k profiles (`profiles:search-benchmark`, bench DB `oppam_bench`)

| Run | Buffer pool | Searches | p50 | p95 | max |
|---|---|---|---|---|---|
| 2026-10-04 (P2.1, decisions) | 512 MB | 200 | 104 ms | 323 ms | 604 ms |
| 2026-11-23 (P9.3c), bench schema migrated to today | **16 MB** (XAMPP default) | 100 | 270 ms | **1,898 ms** | 2,562 ms |

- **What was slow.** The MariaDB slow log was on at runtime only, with `long_query_time = 0.2`, then switched off again.
  - The app's slow statements were all search: the result COUNT and the keyset page.
  - The worst cases filter on detail tables (`nri`, `education_min` → EXISTS on `education_careers`).
  - They examine up to ~114k rows. That is every candidate of one gender.
  - The two slowest statements overall were the benchmark's own setup (count of all active profiles, `ORDER BY RAND()`), not the app.
- **No index is missing.** EXPLAIN of the worst COUNT:
  - `profiles`: ref on `profiles_status_gender_dob_index`, "Using index", ~49k rows.
  - `education_careers`: eq_ref on PRIMARY.
  - `privacy_settings` (hidden profiles) and `ignores`: **MATERIALIZED** once, so a hash lookup per candidate.

  The cost is reading ~49k index entries plus a primary-key lookup per candidate, and with a 16 MB buffer pool those pages
  come from disk. The fix is memory, not an index. The same queries ran at p95 323 ms with 512 MB.
  → P9.5 (existing hand-over): size `innodb_buffer_pool_size` to hold `profiles` + the search tables, and re-run the
  benchmark on staging.
- **The first-payment report** (`LiveRevenue`, NOT EXISTS on `orders`) uses `orders_profile_id_status_created_at_index`
  (profile_id + status prefix), then a member's handful of paid orders. The planned `(profile_id, status, paid_at)` index
  would save almost nothing, so it was **not added**.
- **The audit filter lists:** `DISTINCT action` / `DISTINCT subject_type` are loose index scans ("Using index for group-by",
  84 index entries for 1,449 rows). An expression (`SUBSTRING_INDEX`) would read every row, so the lists keep the plain
  DISTINCT. They are now cached for a day and dropped when a new area or type is written.

## Queries per page (N+1 hunt)
Each page was rendered with a few rows and again with many. The test fails if the second render runs more queries.

| Page | Result |
|---|---|
| Member search | no growth |
| Profile page (similar-profiles strip) | no growth |
| Chat inbox | no growth |
| Notifications | no growth |
| Dashboard daily strip | no growth |
| A03 admin members | no growth |
| Public home (testimonials, banners, featured members) | no growth |
| A09 reports (all five) | within budget |

- **No N+1 was found.**
  - The profile page showed +3 queries only while its similar-profiles strip went from empty to shown: three eager loads
    for the whole strip, confirmed by the reviewer's probe (flat at 101 queries from 1 to 11 similar profiles).
  - The home page's first +1 was **not** a section appearing. The profile factory creates master rows, which bump the
    masters cache version, so the cached country list was re-read once. That is a test artefact; the list is warmed after
    the fixtures.
  - **Correction, review round 1:** the first home dataset never actually showed a featured member. A plain member doesn't
    qualify (premium, verified, opted in, approved photo). The dataset now builds real featured members and asserts the
    band shows them in both renders: still no growth from 2 to 22 of them.
- **Report medians** (ops, revenue, chat first reply): one SQL query each (`SqlMedian`) instead of loading every value into
  PHP. The moderator table uses SQL aggregates plus one grouped median.
- **Production** now logs a lazy load (model + relation) instead of hiding it (`LazyLoadingGuard`).

## Front end (`npm run build`)

| Asset | Before P9.3c | After |
|---|---|---|
| app entry JS | 237.7 KB | **81.7 KB** (29.2 KB gzip) |
| shared chunk the entry imports statically (`preload-helper`, also used by admin) | 157.2 KB | 157.2 KB (unchanged) |
| **JS every member / public / broker page loads** | **~395 KB** | **~239 KB** |
| Swiper | inside the entry | own chunk 156.3 KB (45.7 KB gzip), loaded only on home / dashboard strips / ad rail |
| app CSS | 536.1 KB (89.1 KB gzip) | unchanged |

- **Swiper CSS** stays in `app.css`. The home hero (the LCP element) must lay out before the JS arrives.
- **Home hero:** the first banner is preloaded from `<head>` with `fetchpriority="high"`. Logos, avatars and the preloader
  logo no longer claim high priority on every page.
- **Fonts:** all four weights (400–700) are used. `@fontsource` uses `font-display: swap`, and a weight's file is only
  downloaded when text uses it, so nothing was trimmed.
- **Not changed:**
  - the template's preloader curtain (part of the look, owner's call after Lighthouse);
  - a 960 px banner variant + `srcset` — deferred until Lighthouse shows the mobile LCP needs it. Existing banners have no
    record of a variant, so serving one would need a migration or a per-render file check.
